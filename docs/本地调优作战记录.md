## 事故 1：题面示例 flag 误杀整题 ✅（2026-08-25 15:23 热修）

**症状**：a-05 开题 28 秒连交两个错 flag（`flag{}`/`FLAG{}` 双形态），15 分钟后整题被"部分解出正常收尾"关闭弃掉。d-02 复发同症。
**根因链**：题面含示例 flag 格式串 → agent 抄进星记 → `extract_flags` 捞走提交（+2 错交）→ 错交触发 20min 近失预算 → 到点收尾时 `flags_found` 非空 → 走 partial-close 分支不回队 → 整题白丢。
**解法（已落代码）**：`collect_flags_from_facts(descriptions, exclude_texts)` 增加题面原文排除——题面出现过的 flag 串一律不收集（答案只可能来自靶机实测输出）。四个调用点已接线（`[result.description]`/`[goal]`）。
**验证**：热修重启后错交数冻结在 4，未再增长。
**波及面判断**：e/f 系列（WAF 题，题面带 payload 示例）共 17 道，此修复保住潜在 6000+ 分。

## 事故 2：重启后双引擎竞态，25 分钟空转 ✅（2026-08-25 15:45 根治）

**症状**：换心重启后题目起了但星图 0 facts、全 worker 停滞、`create_hint 404 Project not found`、e1 双题槽位自旋刷屏。
**根因**：旧树未杀干净（bash `$!` 拿到的是 venv shim PID，taskkill 杀不到真身）→ 残留进程与新生引擎竞争 → serve 换血（先起后死，proj 建在死库）→ 现役 serve 空库 → 三题对不存在的星图空转。
**解法（SOP 已固化）**：
1. 杀 runner 前先 `powershell Get-CimInstance Win32_Process -Filter "Name='python.exe'"` 拿全量 PID+CreationDate+CommandLine；
2. 按启动时间分树杀，无关进程（http.server 等）保留；
3. 杀完验证两条：`netstat :8000` 无 LISTENING + python 进程清点符合预期；
4. 重启后盯 3 分钟星图 facts 增长才算成功（不是看"challenge started"日志——起题成功≠引擎在干活）。

## 事故 3：50 分钟断网事件 + 连锁处置 ✅（2026-08-25 16:16-17:25）

**症状链**：16:16-17:08 本机断网（DNS getaddrinfo failed）→ LLM/平台全断 → worker 全停 37min+；c-05/a-07/a-09 开题失败线程死亡；e1-01 收尾时 close 三连失败标 close_failed；runner 主循环活着并饥饿回灌续跑 e1-01。
**处置（按序）**：
1. 断网恢复后手动补关泄漏容器（e1-01/c-03/c-09）——**其中 e1-01 误伤**：实为在打题非泄漏（教训：close 前必须核对 runner 日志该题线程是否存活）；
2. 手动 start 复活 e1-01 靶机，发现**地址漂移**（.97→.96）→ 用 server API `POST /projects/{id}/hints` 注入运维 hint 告知新地址（curl 中文 body 会解析失败，用 python urllib）；
3. dispatch 空转（intents 空闲无人认领，疑似断网期 hang 住的 worker 线程占满池）→ 不深挖，SOP 重启第三次；
4. 重启后 e1-01 以新地址新项目干净开局，三 worker 会话实时写入。

**新增 SOP 条目**：
- 手动 close 平台容器前，先 grep runner 日志确认该题无活跃线程（"challenge resumed/started"近期行）；
- 平台 start 幂等但**容器重建后地址可能漂移**，续跑题需校验地址一致性，漂移则注入 hint 或重开项目；
- 引擎注入 hint 用 python urllib（curl 对中文 JSON body 解析失败）；
- 断网类故障恢复后若 dispatch 超过 5 分钟不派单，直接 SOP 重启，不值得现场debug。

**战果**：恢复后 e1-02 满分解出（250 分，零错交）——题面假 flag 修复在 e 系实战验证通过。

## 事故 4：resume 死锁——completed 项目无限复用 ✅（2026-08-25 19:07 根治）

**症状**：星图冻结一小时（分数 3200 停滞）；重启后复发；日志 `reactivate_project failed 409` 每 11 秒循环；引擎里唯一项目已 completed。
**根因链**：某题假归航（引擎 complete 但平台无 flag）→ defer 回队 → resume 复用 project_id → reactivate 409（completed 是终态不可逆）→ **异常被吞、继续对着不会再有产出的星图轮询** → 无限 defer/resume 循环，题线程空转、槽位被占死。
**解法**：`reactivate_project` 改为返回成功与否（终态/不存在 → False）；runner 收到 False 即**放弃复用、新建项目重打**（丢星图远好于死锁空转）。同时落地**半死看门狗**：活跃题存在但星图 15 分钟零增长 → 进程自重启（ASTRA_STALL_SECONDS 可调）。
**自愈体系至此成型**（四层）：网络瞬断题不死 → 泄漏容器清道夫 → 全停看门狗 → 半死看门狗（星图增量脉冲）。

## 事故 5：busy_count 字段漏定义炸线程（2026-08-26 第二轮 14:40 热修）

**症状**：槽位满时开新题 → `AttributeError: 'ChallengeResult' object has no attribute 'busy_count'` → `_work` 线程炸死（ slots dataclass 不允许动态属性——加 transient_count 进了字段，busy_count 漏了）。
**解法**：busy_count 补进 ChallengeResult 字段，`getattr` 式自增简化为 `+=`。SOP 重启换码，重启后 AttributeError 归零。
**教训**：给 slots dataclass 加运行态计数的任何路径，必须同步进字段声明——测试没覆盖 SlotBusy 分支所以没拦住（记 TODO：补 busy 退避单测）。

## 事故 6：VPN 断裂耗尽自愈预算 + 平台关账（2026-08-26 第二轮终局）

**时间线**：16:25/16:42 看门狗两枪（第 2/3 次）→ 第三枪后重启撞 VpnCheckError 崩溃 → 预算（4h/3 次）打光 → runner 死亡 1h+ → 我方 SOP 重启也死于 VPN 检测 → 确认 SSLVPN 隧道断（靶机 10.0.185.x 全 000，平台公网 API 正常）→ 挂自动续跑哨 → **平台任务关账（invalid_state）**，第二轮定格 10/63、2900 分。
**教训与改进项（赛后）**：① VPN 断裂期不应消耗自愈重启预算——应先探靶机可达性，不可达则挂起等待而非重启（预算留给引擎侧故障）；② SDK VpnCheckError 应纳入 TransientNetError 家族带耐心重试而非启动即崩；③ 本地跑对 SSLVPN 稳定性依赖重，长窗跑分前提醒用户检查 VPN 客户端保活。
**第二轮净产出**：看门狗半死检测实战首杀（16min 自愈 vs 昨日 1h 人肉）；busy_count/deque 并发两起热修；c 系开局三连杀验证假 flag 免疫稳定。
