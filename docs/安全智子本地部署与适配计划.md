## 当前实现

1. `dispatch.secsophon.example.yaml`：local execution、单 Pi worker、loopback 模型端点和 `openai-completions` 协议；决定、执行和核验共用本地模型，避免任何云端回退。离线模型 profile 会显式传 `--no-mcp`，防止 `--tools` allowlist 之外的 MCP 服务器被发现。
2. `offline_model_policy`：配置加载时对每个 Pi worker 的 `PI_BASE_URL` 做 fail-closed 检查。`loopback` 只接受数字回环地址；`private_lan` 还允许 RFC1918/ULA 地址。主机名、带凭据/查询的 URL、外部云端 URL 都拒绝。
3. `scripts/secsophon_preflight.py`：检查 Pi 1.1.0、模型目录、离线辅助模型变量；可选真实 smoke test 会让 Pi 使用 `read` 读取临时文件，再续跑同一 session。输出工具调用数、会话、耗时和结果，不上传权重或数据。
4. `container/Dockerfile.spark`：以 ARM64 可用的 Node 22 + Python 3.12 基础镜像准备 ASTRA/Pi 包。它不打包模型权重、推理服务器或 Kali x86 二进制，必须等主办方公布交付契约后再补。

## 本机预检记录

机器是 Windows x64、24 核 i9-13900HX、约 64 GiB RAM、RTX 5080 Laptop 16 GiB；Docker 服务报告 `x86_64`，不是 DGX Spark ARM64。Ollama 已有 `qwen3.6-35b-a3b-hauhaucs:q4_k_m`（约 21.9 GB，Q4_K_M），没有下载新权重。

运行：


`--require-arm64` 用于到 Spark 后把“ARM64 预检”升级为设备门槛检查；在当前机器上应失败，这是预期行为。

## 到设备后的顺序

1. 先拿到正式镜像、模型、权重导入和网络政策；将它们写成合同测试，不复制主赛 AMD64 镜像。
2. 在两台 Spark 分别执行版本、模型目录、离线 DNS/出口、显存/内存和单请求预检；记录温度、功耗、首 token、总时延和并发。
3. 运行同一文件读取/写入工具闭环和 session 续跑；再测单机故障、状态恢复、两机是否允许共享状态。
4. 只有主办方允许且实测通过后，才配置双机分工、并发和安全工具；权重、凭据、题目数据和现场日志不提交仓库。

## 当前停止条件与风险

- 未确认题型和评分前不做模型微调或大规模工具铺设；先保证本地模型调用稳定、可续跑、可审计。
- `Dockerfile.spark` 尚未在真实 ARM64 主机构建；当前网络无法访问 Docker Hub 时也不能把镜像构建写成已通过。
- 21.9 GB 模型在 16 GiB 显存上会发生 CPU/GPU 混合，时延仅用于本机代理基线；不能外推 DGX Spark 性能。
- `ASTRA_EMBED_API_KEY`、`ASTRA_EMBED_MODEL` 和 `ASTRA_LLM_API_KEY` 在离线 profile 下会导致配置加载失败，防止隐藏的云端辅助路径。
- `offline_model_policy` 和 `--no-mcp` 只约束模型端点与 MCP 发现；当前 `local` 执行仍可使用 ASTRA 原有 shell 工具，不能等同于整个 Agent 的网络隔离。若现场要求工具网络完全离线，必须在官方允许的容器/主机出口上再做拒绝测试，并据实更新配置。
