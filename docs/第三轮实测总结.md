## 二、本轮遇到的所有问题（按时间序）

### 1. GLM-5.3 Anthropic 端点不支持工具调用（本轮最大事故）
- **现象**：dsh 发给 GLM 的请求含完整 24 个工具定义，但 GLM 会话 443 个事件 **0 次 tool/use**，全是 `reasoning-chunks`（空想不干活）
- **验证**：直接 API 测 get_weather 工具，GLM 返回 thinking + 介绍文本，无 tool_use 块；`open.bigmodel.cn` 和 `api.z.ai` 两个端点都一样
- **影响**：GLM 阶段 e1/e2 能解（纯文本推理碰对），a/e3 需要工具探测的题全部卡死；浪费 21:28~23:30 约 2 小时
- **根因**：GLM-5.3 的 Anthropic 兼容端点工具调用实现不完整（或需特定参数/模式）

### 2. GLM bootstrap 任务超时（315s/615s）
- 现象：bootstrap 稳定超时，从 300s→600s→900s 放宽仍超（GLM 单任务 615s）
- 根因：GLM 深度思考 + 不执行工具 → 任务无限拖长
- 这是 GLM 问题的伴生现象，非独立缺陷

### 3. 任务超时与 worker 饥饿（DeepSeek 阶段）
- **bootstrap 375s 稳定超 360s**：DeepSeek 服务端当前负载高或 key 被限速，bootstrap 需 375s
- **难题占满 3 worker**：e3-04/a-03/a-13（hard）反复"提案→审查否决→重拟"，占槽 1-2 小时
- 后续 a-15/16/17、a-18/b-01/b-02 同样占槽到超时

### 4. reason 提案审查否决循环
- 现象：`verdict rejected proposal` 反复出现，模型提案被审查否决后重拟
- 这是引擎的**防无效探索设计**（防止写无证据假设），对难题正确但耗时
- 第二轮同样存在，非本轮新问题

### 5. 模型 key 配额（延续第二轮教训）
- 本轮 GLM 免费额度正常；DeepSeek key2 从 25.66 元消耗到 18.50 元（约 7 元/2 小时）
- 若跑满 6 小时需准备更多余额或双 key

## 三、下次改进方案（按优先级）

### P0：模型选择——必须工具调用正常
- **验证清单**：接入前先跑 `container/dsh/e2e_verify.py`（4 项：基础调用/执行/会话续接/落盘）+ **工具调用专项测试**（给 get_weather 工具确认返回 tool_use 块）
- **GLM 结论**：Anthropic 端点工具调用不可用，**不要用 GLM 跑分**（除非确认其 OpenAI 端点 glm-5.3 可用且余额充足）
- **首选**：DeepSeek（已验证工具调用正常、稳定出分）

### P1：提前预检 + 双 key 轮换

### P2：任务超时按模型自适应

- 但**难题占槽**是更大的吞吐损失：考虑"难题超时轮换"策略——hard 题 45 分钟无 flag 即换简单题（defer 机制已实现，可调低 defer 阈值）

### P3：难题策略

- 建议：**跳过已知难题**（`--skip-codes`），把槽位给 d/f/c 快速加分系列
