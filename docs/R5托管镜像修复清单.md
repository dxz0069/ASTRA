## P0（必改，直接决定托管跑分吞吐）

### 1. defer 僵尸项目饿死新题（今晚最大 bug）
- **现象**：题目 45 分钟 defer 后，平台容器已关，但引擎项目保持 `active` 继续抽 worker
  攻击已死靶机；同时占用 `max_running_projects` 预算，新启动题 40 分钟零调度。
  两次人工删除僵尸后，被饿的 f1-02/f1-03/f2-08 在 4-8 分钟内全部破防（非能力问题）。
- **根因**：`container/astra_runner/runner.py:318-337` defer 分支对引擎零调用。
- **修复**（引擎机制已齐，只差接线）：
  1. defer 时 `PUT /projects/{id}/status` → `stopped`（`astra/src/astra/server/routers/projects.py:188`
     已实现：清 worker 租约 + reason 状态；状态枚举 `active|stopped|completed` 见 models.py:54）
  2. 回队复用项目前，`stopped` 状态先 `POST /projects/{id}/reopen`（projects.py:325 已有）
  3. 调度器派发前校验项目状态必须 `active`（防御性硬约束，scheduler/loop.py）
  4. 停止项目时走与 delete 相同的在途任务取消路径（TaskCancellation，已存在）
- **验收**：单测 defer→stopped→后续 N 轮零调度；requeue→reopen→带星图恢复；defer 上限→删除不变。

### 2. 模型输出 markdown 围栏解析失败
- **现象**：合法 JSON 被 ```` ```json ```` 围栏包裹 → `accepted must be true or false`
  解析失败，丢完整决策周期（内容质量很高，纯格式问题）；bootstrap conclude 同样中招。
- **修复**：output_parser（astra/src/astra/dispatcher/output_parser.py）解析前剥离首尾
  markdown 围栏/杂散空白；解析失败时降级日志附带原始输出前 500 字。
- **验收**：围栏包裹的 verdict/reason/conclude JSON 全部可解析。

### 1b.（第二层保险）runner 定时对账扫描——用户提案的修正版
- **背景**：用户原提案"已完成项目达 8-10 个触发清理"不可行：僵尸是 defer 后仍 active 的项目
  （completed 项目本就不调度）；且完成数触发与损害互斥（僵尸饿死新题→完成数停涨→清理永不触发）。
- **修正方案**：runner 主循环每 5 分钟对账——拉引擎 active 项目列表，对照当前活跃窗口的
  code↔project 映射，**active 但不在窗口且创建超过 60s 的项目 → `PUT status=stopped`**。
- **定位**：defer 直连 stopped（1a）为主治，对账扫描兜底所有泄漏路径（崩溃/竞态/未知 bug 的孤儿项目）。
- **验收**：人为制造孤儿项目（跳过 defer 直接关平台容器），5 分钟内被对账停掉。

## P1（强烈建议）

### 3. dsh 会话丢失税（全程 13+ 次 × 600s 超时槽）
- **现象**：`dsh: resume failed for session-X (not found), creating session`，任务空烧满
  600s 超时；曾出现同项目两 worker 同分钟同时丢会话（指向 dsh home 清理/会话保留策略）。
- **排查方向**：`astra_runner_engine.py` 的 `_cleanup_dsh_home`（引擎启动时清理）与 dsh
  会话保留时长；至少改为：resume 失败立即快速失败重派（不等满超时）。

### 4. watchdog 告警文件陈旧误报 + 探针过敏
- **现象**：上轮残留告警文件未清（07:23 的告警差点误判本轮）；智谱端点整点抖动
  （22:15/00:08/00:57 三波，2-5 分钟自愈、会话 403=0）连续 2 次即落盘告警。
- **修复**：watchdog 启动时删除旧告警文件；探针失败阈值 2→3 次或探针超时加长，
  且真实任务会话 403 才升级为告警（探针超时单独记日志）。

### 5. 关题竞态 404 噪声
- **现象**：平台侧完成 → 停引擎项目 → 在途 reason 任务写结果 404 级联
  （review failed 0xC000013A → reason complete write failed → 降级放行），浪费一个决策周期。
- **修复**：停项目先取消在途任务再清理；任务侧对 404 写入静默退出。

### V2-7.（新特性）满窗口利用——不提前结束
> 用户需求（2026-08-16）：用满全部 6 小时。Run 10089 实证：15:10 提前 29 分钟结束——
> 队列耗尽（16 题全部 defer 上限弃赛）+ 开题判据过保守（剩余<48min 即视为"放不下一题"）。
> 平台侧允许跑满全程，提前退出纯属 runner 自身规则。

1. **饥饿回灌（核心）**：当队列为空（无未尝试题、未弃赛题、或剩余时间放不下任何新题）
   且剩余窗口 >15min 时，**无视 defer 上限**按 EV 重启已弃题：
   `wrong_count>0（近失）> 多 flag 有余量 > 有星图/hint 积累 > 分值高`。
   defer 上限只在"还有别的题可开"时生效——没得选时，攻旧题永远优于空转。
2. **期望预算开题判据**：开题的剩余时间判断从"最长单题 48min"改为该题期望预算：
   有 KB 条目 → `max(2×首解耗时, 15min)`；近失/playbook 题 → 20min；无参考 → 按难度
   `DIFFICULTY_TIMEOUTS`（runner.py:494 已有分难度超时）。尾段也能开短题。
3. **多 flag 余量扫尾（可选）**：最后 20min 若无题可开，对"已解但 total_flag_count >
   已得数"的题做余量 flag 扫荡（bctf-09 型三 flag 题实证存在多 flag 面）。
4. **不提前退出**：主循环只在窗口到点（或平台 409）时收尾；队列空 → 触发 1 的回灌。

- **10089 对照**：尾段 29 分钟空转 + ATLAS 差一步（2 错交）——本特性下这 29 分钟
  自动变成 ATLAS 第 5 次尝试或 AURORA 续攻。
- 与 V2-0（已撤销）的区别：不强制触达、不改开题顺序/时间预算——只在"无事可做"时
  把空闲槽位回灌给期望值最高的旧题，是对浪费做减法。
